# Rep → MP4 录制器（ReplayDnD + OBS）

把非想天则的 `.rep` 文件**直接拖进来**，程序会依次自动播放每一场，并用你电脑上的 OBS 录成 mp4。
一次拖 10 个、20 个都行，会一个接一个排队录完。

> 本机已验证通过：OBS 32.1.2（`D:\obs\obs-studio`）+ obs-websocket 5.7.3，
> 实测单文件 26.9 MB / 44 秒、批量 56.0 MB / 53 秒，录到的是游戏画面（自动截图存 `RepRecorder.lastframe.jpg`）。

---

## 一、一次性准备

1. **OBS**：已装好即可，程序会自动找到它（支持 `D:\OBS\obs-studio` 这类非默认路径，会读注册表和各盘根目录）。
2. **WebSocket**：程序会在 OBS 没运行时**自动帮你启用**（`工具 → WebSocket 服务器设置 → 启用`），密码也会自动读取。
3. **采集源**：不用手动配。程序会建一个专用场景 **`RepRecorder 录制场景`**，里面放一个窗口采集源 **`RepRecorder 游戏窗口`**，
   每次录制前自动把它绑定到非想天则窗口，并按画布居中适配（不会去用你的「显示器采集」，所以不会录进整个桌面）。
4. **编码器**：务必自己改一下 —— OBS → 设置 → 输出 → 录像 → 编码器改成 **NVIDIA NVENC AV1 / H.264**。
   > ✅ **2026-09-26 复核**：显卡驱动已经是 **617.14**（之前记录的 546.26 太旧，OBS 的 `obs-nvenc.dll` 当时加载
   > 不了才只能走 CPU 软编 x264）。现在驱动够新，OBS 里可以直接选 NVENC；ffmpeg 的 `h264_nvenc` 也确认可用
   > （并行切分一直在用它，工作正常）。
   录像格式建议保持 `hybrid_mp4`（就算中断也不会生成打不开的文件）。
5. **游戏侧**：保持 `ReplayDnD-old` 启用（双击播放的那个），`ReplayDnD.ini` 里 `AutoShutdown=1`（播完自动关游戏，程序靠这个判断录完）。

## 二、日常使用

- 打开 `RepRecorder.exe`，把 `.rep` **多选拖进窗口**（整文件夹也行，会递归找 .rep），松手即开始。
- 也可以把 rep **拖到 exe / 桌面快捷方式图标上**。
- 列表里能看到每个文件的状态；双击一行可在资源管理器中定位文件。
- 录好的文件放在**对应 rep 旁边**，文件名与 rep 相同、扩展名 `.mp4`。

**界面小改动（2026-09-25）**：
- **拖进去不会自动录了**：默认只把 rep 放进队列，等你点「开始录制」才开录。
  想恢复"松手就录"，把界面上的「拖入后自动开始」勾上（对应设置 `AutoStartOnDrop`，默认已改为关）。
- **窗口缩小也不会漏掉按钮**：顶部区改成自动换行布局，最小 640×420 时所有按钮/勾选项都完整可见。
- **「刷新」按钮**：重新检查队列里每个 rep 到底有没有录好的视频。
  你把视频删掉之后点一下，那一行就会从「已录制」变回「等待」，可以直接重录（不用重新拖 rep 进来）。
  刚拖进来的 rep 如果已经有视频，也会直接显示成绿色「已录制」。
- **声音只用一个按钮**：`声音：开 ✓`（绿）/ `声音：静音 ✕（录完自动恢复）`（红），**点一下切换**，
  颜色和文字实时反映当前状态（每 2 秒和系统真实状态同步一次）；录完会自动把声音恢复。
- **不再自动关闭 OBS**：想让它录完关掉，勾上界面上的「录完关闭 OBS」即可。
- **主界面去掉了「准备时把 OBS 画布设为 1440×1080@60」那个复选框**：
  它和「准备 OBS」按钮不是一回事（按钮是动作，复选框只是"动作里要不要顺带改画布"的开关），
  而且同一个开关在「设置…」里本来就有（分类**画布 → `AutoCanvas`**），所以主界面不再重复放一个。
  你之前是勾上的，行为不变（画布照样会设成 1440×1080、左右无黑边）；想改就去「设置… → 画布」。

**「准备 OBS（自动建源+绑定窗口）」 vs 「仅打开 OBS」**（两者挨在一起放，功能不重复）：
- **准备 OBS（自动建源+绑定窗口）**：启动并连上 OBS，**自动创建/检查采集源、把游戏窗口绑上去**
  （若「设置…→画布→AutoCanvas」是开的，还会把画布/帧率设成 1440×1080@60）。平时点这个就够了。
- **仅打开 OBS**：只启动 OBS，**不改任何设置**（适合你想自己进 OBS 调编码器/场景）。
  > 之前点「打开 OBS」会弹 `Failed to find locale/en-US.ini`：那是程序启动 OBS 时**没设置工作目录**的 bug
  > （OBS 必须从它自己的 `bin\64bit` 启动才能找到 `locale/`），并且 .NET Framework 的 `ProcessStartInfo`
  > 默认 `UseShellExecute=true` 时工作目录语义不可靠。已修复（显式设工作目录 + `UseShellExecute=false`）。

**程序在哪：** `RepRecorder\RepRecorder.exe`；整合包根目录有现成的快捷方式 `Rep录制器.lnk`（拖到桌面即可）。

## 三、设置项（`设置…` 按钮，存于 `RepRecorder.settings.json`）

| 设置 | 说明 |
|---|---|
| `ObsExe` / `GameDir` | OBS 与游戏路径，留空自动搜索 |
| `Port` / `Password` | obs-websocket 端口与密码；密码留空自动从 OBS 配置读取 |
| `MaxMinutes` | 单个 rep 录制上限，超时强制结束（默认 12 分钟） |
| `PreRollSeconds` / `PostRollSeconds` | 开录前 / 停录前的等待秒数（默认 3 / 2） |
| `AutoStartOnDrop` | 拖进来就自动开始 |
| `AutoPrepareObs` | 自动准备采集源并绑定游戏窗口 |
| `UseDedicatedScene` | 用专用录制场景（只录游戏窗口）；关掉则用你当前场景已有的源 |
| `MicMode` | `gameOnly` = 只录游戏声音（录制时自动静音麦克风）；`gameAndMic` = 游戏声音 + 麦克风（边录边解说）。界面上有「录音模式」下拉框可直接切 |
| `RecordGameAudio` | **界面上有按钮**：`录游戏声：开 ✓`（绿）/ `录游戏声：关 ✕`（灰），点一下切换。决定**录进视频里**有没有游戏声音：开 = 正常录（音效/BGM）；关 = 视频无声（适合之后自己配 BGM）。和左边的「声音」按钮完全独立 —— 那个只管**你自己耳朵**听不听得到 |
| `RecordBgm` | **界面上有按钮**：`录BGM：开 ✓` / `录BGM：关 ✕`。决定录像里有没有**背景音乐**——点它会把 `ReplayDnD.ini`（含 `ReplayDnD-old`）的 `MuteMusic` 改成 `0`/`1`，因为游戏是启动时读这个 ini 的，所以**下一个文件开录时生效**。默认关（整合包默认就是 `MuteMusic=1`，没有 BGM）。⚠️ BGM 有版权风险 |
| `ParallelCount` | 一次同时开几个游戏实例（界面上有「**同时录制数量**」下拉，**1~6**）。1 = 相当于普通单录。上限锁 6 是因为 OBS 只有 6 条音轨 —— 再多就没法给每格单独放声音，会录出没声音的视频 |
| `GameAudioOnly` | 只把游戏声音录进视频：新增「应用程序音频采集(th123.exe)」，并临时静音 OBS 桌面音频（默认开） |
| `MuteGameForMyEars` | 每次开始录制时自动静音**默认输出设备**：录制期间你什么都听不到，录像里仍有完整游戏原声，录完自动恢复。**界面上有勾选项**「录制时自动静音（听不到游戏）」，单录/并行都生效。代价与原因见第十一节第 9 条 |
| `AskSaveLocation` | 每录完一个视频就弹窗问你要放到哪里（默认开） |
| `LastSaveFolder` | 「另存到文件夹…」上次用过的文件夹 |
| `SkipExisting` | 已有同名 mp4 的 rep 直接跳过（批量重拖省时间，默认开） |
| `AutoCanvas` | 「准备 OBS」时是否把 OBS 的画布/输出分辨率与帧率设成下面的值。非想天则原生是 4:3 的 640×480，用 1440×1080 这种 4:3 画布画面正好铺满、**左右没有黑边**；不勾就用你 OBS 自己的画布（你现在是 1920×1080，4:3 画面会居中、左右各留黑边） |
| `CloseObsAfter` | 录完是否关闭 OBS。**默认关**（程序不再自动关 OBS）；界面上有勾选项「录完关闭 OBS」 |

## 四、程序为你做的事（自动）

- 自动启动 OBS（最小化到托盘）并连接 WebSocket
- 自动创建/复用专用场景与窗口采集源，并绑定到非想天则窗口
- **黑屏自愈**：开录前对采集源截图检查，全黑就自动换捕获方式（自动 → BitBlt → Windows 图形捕获），日志会写明用了哪种
- 把 OBS 录像目录临时指到 rep 所在文件夹，队列结束后**还原**成原来的目录
- 队列结束后把节目场景**切回你原来的场景**
- 校验产物是否含 `moov` 索引（缺了就提示"可能不可播"）

## 五、常见问题

- **录像里想只留游戏声音（不要自己的麦克风）**：工具栏「录音模式」下拉框选 **只录游戏声音**，
  程序会在录制时自动静音麦克风（含 OBS 全局设备「麦克风/Aux」），录完恢复原状态。
  想边录边解说就选 **游戏声音 + 麦克风**（录制时会自动打开麦克风，录完同样恢复）。
  ⚠️ 注意：旧版本"录制途中切换模式不生效"的 bug 已修复（现在会立即生效，并且每个文件开录前都会再确认一次）。
- **OBS 里出现一堆同名音频源**：旧版本每跑一次就往场景里多加一个 `RepRecorder 游戏声音` 元素导致的
  （OBS 允许同一个源在一个场景里放多份）。**已修复**：现在会自动清理，日志会写
  `清理了 N 个重复的「RepRecorder 游戏声音」元素`。你也可以手动把多余的删掉，程序会保留一个。
- **录完问我把视频放哪**：录完会弹窗，可选「留在 rep 旁边」「另存到文件夹…」「以后不再询问」，
  还有「本队列后面录好的视频也都这样处理」勾选框。批量录制时勾上它就不会被问 10 次。
- **前半段黑屏**：根因是捕获方式。窗口采集在「自动」模式下会退化成 BitBlt，而
  **BitBlt 抓不到被其他窗口完全挡住的内容** —— 录制时你如果让 OBS 或别的窗口挡在游戏前面，那段就是黑的。
  现在程序**优先使用 Windows 图形捕获(WGC)**（能抓被遮挡的窗口），并且录制中每 5 秒自检一次，
  一旦发现画面变黑就自动切换捕获方式尝试恢复，日志会写明。
  录制期间请尽量别让别的窗口完全挡住游戏窗口。
- **录像里出现了两个游戏画面（一大一小）**：这是早期版本的 bug —— 程序每次运行都往专用场景里重复添加同一个采集源，
  OBS 允许同一个源在同一场景里放多份，只有第一份被缩放到满屏，其余几份是原始 640×480 贴在左上角。
  **现已修复**：不再重复添加，并且每次准备时会自动清理掉已有的重复元素（日志会写"清理了 N 个重复的采集源元素"）。
- **录像没有背景音乐**：`ReplayDnD.ini` 的 `MuteMusic=1` 会静音 BGM（只留音效）。想要 BGM 改成 `0`（注意 B 站版权检测）。
- **画面发暗/发黑但程序说正常**：看 `RepRecorder.lastframe.jpg`，那就是开录瞬间采集到的画面。
- **想批量重录**：关掉设置里的 `SkipExisting`，或先删掉同名 mp4。
- **不想要那个专用场景/采集源**：在 OBS 里直接删掉 `RepRecorder 录制场景` 和 `RepRecorder 游戏窗口` 即可，程序下次会重建。
- **录制期间**别切窗口、别乱点鼠标 —— 这是实时录屏，录的是窗口画面。
- **为什么不能像 ReplayDnD 那样 20 倍速**：内置快录走 Media Foundation + D3D9 表面，在这台 N 卡机器上会崩溃/卡死（详见上级目录 `RepRenderTest.ps1`），
  所以这里只能 1:1 实时录：5 分钟的录像就要录 5 分钟。
- **放大到 1080p**（游戏原生 640×480，程序已按画布居中适配）：
  `ffmpeg -i in.mp4 -vf "scale=1440:1080:flags=lanczos" -c:v h264_nvenc -preset p6 -tune hq -rc vbr -cq 23 -b:v 0 -c:a copy out_1080p.mp4`

## 七、关于「按住 A 加速播放，最后导出原速视频」

**实测结论（2026-09-25，重测后有效）**：A 键加速**真实存在**，而且**必须让游戏窗口真正拿到焦点**才生效
（平时你需要用鼠标点一下游戏框就是这个原因）。

| 操作 | 播放用时 |
|---|---|
| 正常播放（对照） | 35.1 秒 |
| **抢到焦点 + 点一下窗口 + 按住 A** | **10.7 秒 → 约 3.3 倍速** |
| 之前测的"按住 A"（没抢到焦点，无效实验） | 35.0 秒 |

所以"加速录制、导出原速"**技术上可行**，但要同时满足：

1. **加速时游戏仍在逐帧渲染**（不是跳帧），并且 **OBS 录制帧率 ≥ 60 × 倍速** —— 3.3 倍速就要录 **200~240fps**。
   只用 60fps 录再降速，画面会一顿一顿。
2. **录完用 ffmpeg 把时间轴拉回来**（需要先装 ffmpeg）：
   ```
   ffmpeg -i in.mp4 -filter:v "setpts=3.3*PTS,fps=60" -filter:a "atempo=0.303" -c:v libx264 -crf 16 out_原速.mp4
   ```
3. 倍速会随机器负载小幅浮动，最好校准一次（同一 rep 录两遍：正常一遍、按住 A 一遍，用时长比算倍速）。

⚠️ **两个现实问题**：
- 让游戏拿到焦点意味着**录制期间你不能同时干别的**（焦点被游戏占着、还要按住 A）——
  这和你"一边录屏一边做别的事"的诉求是冲突的，需要你取舍。
- 你现在是 x264 软编，1920×1080@240fps 做不到。要走这条路至少要：更新 NVIDIA 驱动 → OBS 换 NVENC →
  画布降到 960×720 或 640×480 → FPS 设 240。

**如果你想做，告诉我你接受哪种方式**：(a) 程序自动抢焦点+点窗口+按住 A（录制时不能动电脑）；
(b) 你自己按住 A，程序只负责高帧率录制并在录完后自动降速。

## 八、一边录屏一边干别的

### 想一边录一边干别的：**别最小化，用别的窗口盖住它就行**（实测可行）

- ❌ **最小化游戏窗口 → 录出来是黑屏**。原因：窗口一旦最小化，Windows 就不再为它做桌面合成，
  任何窗口采集方式（WGC / BitBlt）都只能拿到黑屏。把窗口挪到屏幕外也一样（实测同样黑屏）。
- ✅ **用别的窗口把它盖住（不最小化）→ 画面完全正常**。实测：用最大化的窗口盖住游戏 24 秒，
  程序一次「画面变黑」告警都没有，录出来 85.2 MB 正常视频。
  （因为用的是 Windows 图形捕获(WGC)，遮挡不影响采集。）
- 程序还加了一层保护：录制中一旦发现你把游戏窗口最小化了，会**自动把窗口还原**并在日志里提示
  （避免你不知情地录出一整段黑屏）；这个行为可以用设置 `KeepGameCapturable` 关掉。

**所以想要"眼不见为净"的正确做法**：把游戏窗口**拖到一边 / 让别的窗口盖住它**，不要按最小化。

### 声音

工具栏上有一个声音按钮（点一下切换，颜色和文字/符号反映当前状态）：

- **`声音：开 ✓`**（绿色）：你现在能听到系统声音，点一下 → 静音
- **`声音：静音 ✕（录完自动恢复）`**（红色）：你听不到任何声音，点一下 → 恢复

静音的是**默认输出设备**（端点静音），OBS 的「应用程序音频采集」抓的是**进程音频流**、发生在设备静音之前，
所以**录像里仍然有游戏原声**（已用 OBS 的电平事件实测验证）。

**录完自动恢复声音**：只要这个静音是你用本按钮按下的，队列结束后程序会自己帮你打开，
日志里会写 `录制结束：已自动恢复系统声音（录制时你按过静音）`。
（如果你是在 Windows 里手动静音的，程序不会去动它。）

**不想每次手点**：工具栏第 2 行有勾选项 **「录制时自动静音（听不到游戏）」** —— 勾上后每次开录（单录/并行都算）
自动静音、录完自动恢复；万一程序被强制结束没恢复，下次启动会自动帮你把声音打开（靠程序目录里的
`RepRecorder.已静音待恢复` 标记文件判断）。详见第十一节第 9 条。

> **实测记录（2026-09-25，已用 OBS 的 `InputVolumeMeters` 事件自动验证）**：
> - ❌ **按进程静音**（`ISimpleAudioVolume::SetMute`）：**会把录像里的声音一起掐断**（你听过，那段是哑的）。
>   原因是 OBS 的进程音频采集取样点在音频会话静音之后。按钮**不再使用**该方式（只留命令行 `--game-sound` 供诊断）。
> - ✅ **端点静音**（静音默认输出设备，按钮现在用的就是它）：**不影响采集**。实测数据：
>   - 正常录制中：`RepRecorder 游戏声音 = 0.032 / 0.172 / 0.147 / 0.073 / 0.072 / 0.163`
>   - 按下【静音】后：`RepRecorder 游戏声音 = 0.216 / 0.096 / 0.102 / 0.107 / 0.078 / 0.116` ← **照样有电平**
>   结论：按【静音】时你自己听不到，**录像里仍然有游戏原声**。
>   ⚠️ 代价：静音期间**你电脑上所有声音都会没有**（包括你在看的视频/音乐），因为它是设备级静音。
>   若想"只静音游戏、其他声音不受影响"，那需要虚拟声卡方案（见下）。

### 音频自检（新增）

程序订阅了 OBS 的音频电平事件，录制中每 30 秒打印各源状态，录完做一次判定：

```
音频电平第1次：桌面音频 = 0.020（源已静音→不进录像） | 麦克风/Aux = 0.016（有声音，会进录像） | RepRecorder 游戏声音 = 0.190（有声音，会进录像）
音频自检：游戏声音正常（最大电平 0.313）
```

整段没电平、或游戏音频源被静音，会在日志里直接告警并在列表状态显示"注意"——
不会再出现"录完才发现是哑的"。想手动看电平：`RepRecorder.exe --audio-meter 15`。

### 如果想让"只静音游戏、其他声音照常"：虚拟声卡方案

> ⚠️ **前提提醒（2026-09-27 实测）**：这套方案的**关键一步**是"把 th123.exe 单独指到别的输出设备"，
> 而这需要 Windows 提供"每个程序单独选输出设备"。**这台机器的 Windows 11 23H2（build 22631）没有这个功能**：
> 「音量合成器」里每个程序只有**音量滑块 + 静音按钮**，没有输出设备下拉框（我用 UI 自动化把整页元素导出来确认过），
> 非公开接口 `IAudioPolicyConfigFactory.SetPersistedDefaultAudioEndpoint` 也一律返回 `0x80070005` 被拒绝。
> 所以这套方案在**你现在的系统上做不了**；换 Windows 版本（或等系统更新）才有戏。详见第十一节第 9 条。

1. 装免费的 [VB-Audio Virtual Cable](https://vb-audio.com/Cable/)；
2. Windows「设置 → 系统 → 声音 → 音量合成器 → **th123.exe** → 输出设备」选 `CABLE Input`
   （**只影响游戏**，你其他声音不受影响）；
3. OBS 里加「**音频输出采集 (CABLE Output)**」当游戏声音源（程序可以自动加）；
4. 程序的两个按钮改成控制 **OBS 对这条声卡的监听**：
   【打开声音】= 开启监听（你能听到游戏，有约 0.1~0.2 秒延迟）；【静音】= 关闭监听（听不到，录像照录）。

## 九、想更快录（不损失画质）怎么办

OBS 是**实时采集**：录 1 分钟就得花 1 分钟，这一点没法绕过。能"提速"的只有两条路：

1. **让游戏跑得更快**（按住 A 键约 3.3 倍速，见第七节）—— 你说先搁置。
2. **并行录制**（推荐的"无损提速"）：同时开 2~3 个游戏实例、各播一个 rep，OBS 把它们排成网格一起录，
   录完由程序自动切成多个视频（视频按网格裁切、音频用 OBS 的多音轨分开）。
   这样**同样的时间能录 2~3 场，且不需要加速、不损失画质**（只有一次裁切重编码）。
   代价：CPU/GPU 负载变高，录制期间画面是网格。

画质方面另外两点：
- 现在用的是 **x264 软编 CRF 23**；换成 **NVENC + CQP 18~20** 画质更好（需要先更新显卡驱动）。
- **避免二次编码**：直接录成你最终要上传的分辨率（现在是 1920×1080，游戏原生 640×480 会被放大）。

## 十一、2026-09-26 的改动与并行录制实测

### 1. 「录游戏声」按钮（需求：视频有没有声音由用户决定）

按钮本来就在界面右上角（`录游戏声：开 ✓ / 关 ✕`），这次修的是它**在并行录制里完全不生效**的问题：

- **并行路径**：以前每格的音频源 `RepRecorder P1/P2/P3 声音` 建好之后从来没按开关静音过 → 关掉也没用。
  现在建源、以及每次开录前都会按开关静音，录制**进行中**点按钮也会立刻生效（新加的 `SetInputMuteRaw`）。
- **桌面音频**：以前只有 `GameAudioOnly=1` 时才临时静音桌面音频；现在只要「录游戏声」是关的，
  桌面音频也会一起静音，保证录出来**真的无声**（否则系统声音会漏进视频）。
- 实测（同一条 rep，其他条件不变）：

  | 按钮 | 文件大小 | 时长 | 音频 max_volume | 画面 |
  |---|---|---|---|---|
  | **关 ✕** | 146.59 MB | 39.25 s | **-91.0 dB（真无声）** | 正常对局 |
  | **开 ✓** | 147.20 MB | 39.20 s | -8.5 dB（有原声） | 正常对局 |

  画面变化帧数 1331 / 1319，基本一致 —— 说明**只有音频被切掉，画面不受影响**。
- ⚠️ 想连 **BGM** 一起录：`modules\ReplayDnD\ReplayDnD.ini`（和 `ReplayDnD-old` 那份）里目前是 `MuteMusic=1`，
  **游戏播放 rep 时根本不放背景音乐**，按钮再开也只能录到音效。程序启动时会在日志里提醒这一条，
  想录 BGM 就把 `MuteMusic` 改成 `0`（注意 B 站版权检测）。

### 2. 并行录制：三个真实的坑（都已修）

本次拿 3 个短 rep 实测，顺带查出并修掉了三个 bug：

1. **拖放根本没用，录到的是主菜单**。并行路径原来是「空参数开实例 → 往窗口里投 WM_DROPFILES」，
   实测这版 `ReplayDnD / ReplayDnD-old` **完全不理合成拖放**（投递后游戏一直停在标题画面），
   所以以前并行录出来的 3~4 MB 视频其实是主菜单（单文件录制一直好，是因为它把 rep 当**命令行参数**传）。
   → 现在改成：先空参数开实例把标题/采集源/音轨摆好，**开录后用带 rep 的命令行重启**这三个实例，
   再把窗口标题改回 `th123 #N` 让采集源重新匹配。
2. **每格只录到画面左上角**。采到的源真实尺寸是 **1920×1440**（游戏无边框全屏 + WindowResizer 3 倍窗口缩放），
   而代码按 640×480 摆位置 → 格子里只有左上角一小块（一条血条）。
   → 现在绑定窗口后**回读源的真实尺寸**再反算缩放（`SetTransformFitCell`），实测每格正好渲染成 640×480。
3. **切分成功后不写回队列**：日志里文件名是空的、大小永远显示 `0.0 MB`，列表也一直停在「录制中」。
   → 已回写产物路径/大小，状态变「完成」。
4. **三格录成同一场对局、声音也张冠李戴**（用户实测发现，已修）。
   根因：**OBS 的窗口串格式是 `标题:类名:exe`，程序一直按 `exe:类名:标题` 拼**。
   OBS 日志里能直接看到 `executable: th123 #1` —— 它把窗口标题当成了 exe。
   单文件时只有唯一一个窗口，靠 OBS 的兜底还能抓到；但并行三个同 exe、同类名的实例就会互相抢窗口。
   实测第 2、3 格录到的是同一场对局（PSNR 40 dB = 同一画面），第 1 格又是另一场。
   → 现在按正确格式拼串（`th123 #1:th123_110a:th123.exe`），并且**每次开录前自检**
   「三个格子是否绑到了三个不同窗口」（日志会打印每格窗口串，撞车会打 ⚠）；
   录制期间还有看门狗每秒盯一次窗口标题，防止游戏加载完把标题改回去再次撞车。
   修复后实测：三个成品 PSNR 互相比都是 13~14 dB（三场不同对局），三条音轨也互相独立。

### 3. 三实例并行占用实测（i9 级 8 核 / 32 GB / RTX 4060 Laptop 8 GB）

三次真实对局同时录制，画布 1920×480@60，每 5 秒采一次：

| 项目 | 实测 |
|---|---|
| **3 个 th123 实例内存** | 稳定在 **1.6 ~ 1.68 GB**（每实例约 **540~560 MB**，峰值 1,675 MB） |
| OBS 内存 | 182 ~ 286 MB |
| RepRecorder 自身 | ~65 MB |
| 系统可用内存 | 录制中 16.3 ~ 16.9 GB（空闲约 18 GB） |
| **GPU 利用率** | 平均 **23%**，峰值 **41%** |
| 显存占用 | 峰值 **3,295 MB** / 8188 MB（含 OBS 与系统） |
| 3 个成品 | 135 ~ 140 MB / 46 ~ 49 秒 / 各带自己的音轨（-1.9 ~ -4.7 dB） |

结论：**3 个实例对这台机器很轻松**（内存多 1.7 GB、GPU 只用到四成、显存还有一半）。

复现用的脚本：`验证-三实例并行内存.ps1`（两阶段：先关声音验证静音、再开声音采内存留成品）、
`验证-录游戏声按钮.ps1`（单文件开关对照）、`验证-录游戏声对比.ps1`（同 rep 开关对照 + 抽帧）。

### 4. 同时录制数量 1~6 + 「录制选中的」（2026-09-26 晚）

- 界面上新增 **「同时录制数量」下拉（1~6）** 和 **「录制选中的」按钮**。
  - 「录制选中的」= 只录你在列表里选中的那些 rep（Ctrl/Shift 多选）；选中数超过下拉里的数量就**自动分批**接着录；
    只选中 1 个时**自动降级成普通单录**；**已有录像也会重录**（你明确选了它）。
  - 老的「并行录制×N」按钮含义不变：取队列里最靠前的 N 个「等待」项。
- **上限锁在 6**，因为 **OBS 最多只有 6 条音轨** —— 超过 6 格时每格的声音没法分开，只能录成没声音的视频
  （需求方明确不要这种视频，所以直接不给选）。设置文件里如果存着 7~10，读取时也会夹回 6。
  - 代码里仍保留"超过 6 格就整批静音"的兜底分支（万一以后放开上限），并且会把标准采集源
    「RepRecorder 游戏声音」一起静音 —— 只静音每格音源是不够的：它默认落在第 1 条音轨上，
    会把其中一局的声音漏进来，而切分时 `-map 0:a:7` 取不到第 7 条轨会退化成"随便取一条"，
    结果 6 个成品全是同一路声音（实测 -8.3 dB）。
- **画布上限 4096**：OBS 的画布宽/高上限是 4096，7 格排一行（7×640 = 4480）时 obs-websocket 会直接报
  `baseWidth is above the maximum of 4096.000000` 并把整批搞失败。现在按 `cols = min(N, 4096/640)` 折行，
  切分改成 `crop=640:480:(列*640):(行*480)`。1~6 格是一行，所以这条平时用不到，属于兜底。
- **音频按标题匹配的坑（并行声音张冠李戴）**：OBS 的「应用程序音频采集」用窗口串找进程，
  `priority` 枚举是 `0=按类名 / 1=按标题 / 2=按 exe`，rating 用**标题的字符串距离**算。
  默认 0 时：类名匹配上之后按"标题距离最近"挑 —— 六个同 exe 同类名的窗口一起跑，标题一旦对不上
  （游戏加载时会自己改标题）就会随便挑一个，于是**两格锁到同一个进程**：实测两格音轨逐样本完全相同
  （换个批次撞的还是别的两格，甚至三格）。现在把每格音源设成 **`priority=1`（标题必须完全相等）**，
  对不上就宁可不给声音，等看门狗把标题改回来会自动重新解析到正确的进程。
- 6 实例实测（同一批 6 个短 rep）：**6 列 × 1 行 / 画布 3840×480 / 6 个不同窗口 /
  6 个成品全部有声（max_volume -4.4~-6.6 dB）、15 组两两比对全部不同**（每格确实是自己那局的声音）；
  用时 161 秒；**6 个实例内存峰值 3,353 MB**（约每实例 558 MB，和 3 实例时一致）。
- 相关脚本：`验证-选中录制与数量下拉.ps1`（下拉项数 + 选中 2 个并行 + 分批）、
  `验证-选中单个降级单录.ps1`（只选 1 个 → 降级单录 + 重录已有录像）、
  `验证-六实例并行含声音.ps1`（上限 6：项数 / 每格有声 / 音轨互相独立）、
  `验证-七实例并行.ps1`（7 格两行排布，已不常用，留作折行逻辑的验证）。

### 5. 用户实测报的三个问题（2026-09-26 深夜，已修）

用户自己拿 2 个 rep 并行录，报了三件事，根因是同一个"单文件采集源在并行期间没被藏起来"：

1. **看第 1 格时同时听到两局的声音** —— 单文件用的音频源「RepRecorder 游戏声音」没静音，
   它默认落在**第 1 条音轨**上，于是第 1 格的成品里混进了另一局（它的窗口匹配是"标题距离最近"，会挑到某一局）。
2. **第 1 格对局结束后没停，把另一局（时间更长的那场）接在了后面** —— 那个源的**画面**元素铺满整块画布、
   在格子底下；某局先结束后格子里没画面了，它就从空出来的地方透出来。
   （另外：录制本身要等**所有**实例退出才停，所以先结束的格子后面本来也会跟着一大段内容。）
3. **第 2 格的成品声音不正常** —— 同上，音轨被第 1 格那条混音影响 + 画面/声音可能对不上。

修法（都在 `RunParallelBatch` 里）：

- **并行开始就把单文件那套采集源藏起来 + 静音**（`SetSceneItemEnabled(false)` + 对「RepRecorder 游戏声音」静音），
  结束时按原状态还原；日志会写「已把单文件用的采集源…隐藏、并把…静音」。
- **切分时按每格自己的结束时刻裁剪**：录制中每秒检查各实例，记下它是什么时候退出的，
  切分时给 ffmpeg 加 `-t <该格实际秒数>` —— 先结束的格子不会再拖着后面那一大段。
- **画面源也设 `priority=1`**（只认标题完全相等）。查 OBS 源码发现 `window_capture` 同样有 `priority` 设置
  （`0=按类名 / 1=按标题 / 2=按 exe`，默认 0 会用"标题距离"挑窗口），所以画面源也有挑错窗口的风险。

验证（一短一长两个 rep 并行，短约 40 秒、长约 100 秒）：

| | 修复前 | 修复后 |
|---|---|---|
| 第 1 格时长 | 整批长度（跟着长的走） | **41.8 秒**（就是它自己那场） |
| 第 2 格时长 | 同整批 | 110.3 秒 |
| 两格音轨 | 第 1 格混入另一局 | **互相独立**（前 30 秒平均差 1201） |
| 第 1 格结尾画面 | 另一局的画面 | **还是自己那场**（抽帧确认） |

脚本：`验证-两格并行长短rep.ps1`，抽帧拼图 `验证-两格画面确认.jpg`。

### 6. 开录后第 9~10 秒的一帧黑屏（2026-09-26 深夜，已修）

用户复测 2 格并行，发现两个成品都在**第 9~10 秒**闪了一帧黑。

根因：**"开播后再刷一遍采集绑定"那一步**。给 OBS 的源重设设置会让它把采集设备**重建一次**
（`wc_update` → `force_reset`），画面就闪一帧黑；那一步是在开录之后约 9~11 秒执行的。

修法：**只有窗口串真的变了才重设**。新增 `ApplyCellWindow()`，它记着一份"已经设过的窗口串"，
一样就直接跳过（三次绑定：建源后、带 rep 重启后、开播后再刷 —— 后两次通常都是空转，不再闪黑）；
真的变了才重设，并且在日志里写 `重设采集源绑定 …`，方便以后定位。

验证（同上一短一长两个 rep）：`blackdetect` 检测结果 ——

- 第 1 格：只有 `0.02~4.43s`（读盘）、`5.72~5.97s`、`41.95~42.68s`（对局结束到游戏退出）三段"黑"；
- 第 2 格：只有 `0~5.15s`（读盘）、`6.50~6.75s`、`110.13~111.08s`（同上）；
- **9~11 秒处没有任何黑段** ✅

那两段"读盘期间的黑"是**游戏自己的读盘画面**（黑底 + 小小的少女logo），不是采集故障 ——
抽帧拼图 `验证-黑帧位置确认.jpg` 可以看出来：5.2s / 6.6s 是读盘画面，7.5s 是 `START!` 开场，

### 7. 「录BGM」按钮（2026-09-27）

游戏播 rep 时**放不放背景音乐**由 `ReplayDnD.ini` 里的 `MuteMusic` 决定：
`1`（整合包默认）= 只有音效、没有 BGM；`0` = 有 BGM。所以界面上新增了 **`录BGM：开 ✓ / 关 ✕`** 按钮，
点一下就会**自动改写两个 ini**（`modules\ReplayDnD\ReplayDnD.ini` 和 `ReplayDnD-old\ReplayDnD.ini`）里那一行，
只改 `MuteMusic`，其它内容不动；程序启动时会先读 ini 把按钮状态同步成真实值。

实测（同一条 rep 各录一遍，只改 BGM 开关）：

| | 成品 | 时长 | 平均电平 | 峰值 |
|---|---|---|---|---|
| **BGM=开**（MuteMusic=0） | 83.7 MB | 38.7s | **-23.7 dB** | -7.3 dB |
| **BGM=关**（MuteMusic=1） | 67.9 MB | 37.6s | -26.6 dB | -7.1 dB |

两段音频平均差 1825（明显不同），开 BGM 后整体电平高约 3 dB、文件大 23% → **音乐确实录进去了** ✅
（样本留在 `样本-BGM开.mp4` / `样本-BGM关.mp4`，可以直接听对比。）

⚠️ 注意：BGM 有**版权风险**（B 站等平台会检测），开之前自己判断。

### 8. `/render` 离线快渲：查清了，这台 N 卡机器用不了（2026-09-27）

新版 ReplayDnD 的「快速录制为 mp4」（资源管理器里右键 rep → `render to mp4 with soku`，命令行就是
`th123.exe /render "<rep>"`）**在这台机器上会在渲染到一半时把游戏搞崩**：

- 实测：标题栏显示 `Rendering 9.9s @ 590.3fps`（约 10 倍速，输出文件已经长到 4.15 MB），
  然后弹出 `Error` 框：`Game crashed! Received exception 80000003 at address 547fb938.`
- 解析那个 minidump（`th123\crashes\crash_*.dmp`）：**异常落在 `ReplayDnD.dll` +0x1B938**（Rust panic 陷阱），
  而当时加载的模块里有 `nvEncMFTH264.dll` / `nvEncodeAPI.dll`（NVIDIA 的 Media Foundation 硬编 MFT）。
- 官方 wiki（[ReplayDnD 文档](https://wiki.514.live/mods/AdvancedMods/ReplayDnD.html)）把这一条列为已知问题：
  **"可能只有 AMD CPU 核显可以使用这个 mod"**，N 卡独显/Intel 核显/AMD 独显会出现
  "点了后录了一小段然后卡死不动"、"生成 0KB~几十KB 的无效 mp4"，**原因和解决办法未知**。
- mod 仓库（soku-cn/ReplayDnD）只是空模板、没有源码/更新；本机是 1.0.0（2024-01）。
- 还试过按 wiki 要求**关掉 `SokuDirectXOptimizations`** 再渲（那一项是"录出来速度飞快"的已知冲突），
  结果一样崩。`/render` 也不能和 `Intel 核显特效补丁` 同用。

**唯一还没试的**（需要管理员权限，我没有）：把 Windows 的硬件 Media Foundation 编码器关掉，逼它走软件编码：

```powershell
reg add "HKLM\SOFTWARE\Microsoft\Windows Media Foundation\HardwareMFT" /v EnableEncoders /t REG_DWORD /d 0 /f   # 试
reg add "HKLM\SOFTWARE\Microsoft\Windows Media Foundation\HardwareMFT" /v EnableEncoders /t REG_DWORD /d 1 /f   # 还原
```

副作用提醒（都是 `/render` 的已知行为）：用过它之后**游戏内 Config 的"FPS 显示"会被关掉**（自己去 Config 重新打开）；
每次崩溃会在 `th123\crashes\` 留一个 dump。
9.5s 已经是 `第2戦 ROUND 1` 了。

### 9. 「把游戏的声音切到一个用不到的输出设备」：这台机器做不到，改成了可靠的整机静音（2026-09-27）

需求是："录制的时候我自己不想听到游戏声音，但录像里必须还有游戏原声，别的程序的声音照常。"
想法是给 th123.exe **单独指定一个用不到的输出设备**（送过去就听不到了）。查完的结论是：**Windows 层面不给这个能力**。

**证据一：非公开接口被系统拒绝**

这是 Windows 自己「按程序设置输出设备」用的接口（`Windows.Media.Internal.AudioPolicyConfig`）：

| 步骤 | 结果 |
| --- | --- |
| 取激活工厂（`DllGetActivationFactory` 或 `RoGetActivationFactory` 两种都试了） | ✅ 成功，接口 IID = `ab3d4648-e242-459f-b02f-541c70306324`（Win11 那一支） |
| `GetPersistedDefaultAudioEndpoint`（读） | ✅ 返回 `S_OK`（空值 = 没有单独设置过） |
| `SetPersistedDefaultAudioEndpoint`（写） | ❌ **一律 `0x80070005`（E_ACCESSDENIED）** |

写失败的组合我都试过了，**全部**失败：改游戏进程 / 改**我自己**的进程（下面还确认了自己当时正在出声）；
设备 ID 传 5 种写法（WASAPI 端点 ID、`\\?\SWD#MMDEVAPI#...#{接口GUID}`、光 GUID、SWD 不带接口 GUID、空串）；
`eConsole/eMultimedia/eCommunications` 三个角色。
vtable 槽位也核对过：EarTrumpet 的[接口定义](https://github.com/File-New-Project/EarTrumpet/blob/master/EarTrumpet/Interop/MMDeviceAPI/IAudioPolicyConfigFactoryVariantFor21H2.cs)
里 `Set` 前面正好 19 个占位方法（即第 25 槽），和 SoundSwitch 的实现一致，不是调用姿势的问题。
参考实现：[SoundSwitch `AudioPolicyConfig.cs`](https://github.com/Belphemur/SoundSwitch/blob/master/SoundSwitch.Audio.Manager/Interop/Client/Extended/AudioPolicyConfig.cs)。

**证据二：这台 Windows 11 23H2 的界面上根本没有这个选项**

用 UI 自动化打开「设置 → 系统 → 声音 → 音量合成器」把整页元素导出来看：

```
系统级：ComboBox「输出设备」autoId=SystemSettings_Audio_OutputList_ComboBox   ← 只有这一个，改的是系统默认设备
应用级：每条程序只有 Slider autoId=SystemSettings_Audio_Mixer_App<pid>_Slider + 「将应用设为静音」按钮
        （没有"输出设备"下拉框）
```

也就是说：**程序化改不了，手动也改不了**（Windows 10 时代的"应用音量和设备首选项"页有每程序设备下拉框，Win11 23H2 的
音量合成器没有）。所以这个方案在这台机器上是死的，也不适合发给别人用（换系统版本还可能变）。

**证据三（顺带把另一条路也堵死了）：单独静音游戏的音频会话会把录像一起弄哑**

既然切不了设备，那"只静音游戏的音频会话"行不行？实测**不行**：

| | 成品体积 | 成品音频 mean（ffmpeg `volumedetect`） |
| --- | --- | --- |
| 对照：BGM 开、什么都没静音 | 83.3 MB | **-23.7 dB** |
| 录制中静音游戏音频会话（`ISimpleAudioVolume::SetMute`，8 秒时生效） | 67.3 MB | **-41.1 dB**（差 17 dB） |

录制中 OBS 自己的电平也印证了：`RepRecorder 游戏声音 = 0.000（无信号）`。
原因：OBS 的「应用程序音频采集」取样点在**音频会话音量/静音之后**，所以会话一静音，录像里就没游戏声了
（这正是你之前报的"录出来没声音"那类问题）。**端点静音**则相反：取样点在端点之前，录像不受影响。

**所以现在的做法：录制时静音整个默认输出设备**

- 主界面新增勾选框 **「录制时自动静音（听不到游戏）」**（= 设置里的 `MuteGameForMyEars`，原来只有设置里有、而且并行录制那条路没生效，这次补上了）。
- 勾上后：**单录和并行录制**开始时自动静音默认输出设备 → 你什么都听不到 → 录完自动恢复。
- 录像里**每格**仍然有各自的游戏原声（并行时是每格一条音轨）。
- **防呆**：静音时会在程序目录留一个标记文件 `RepRecorder.已静音待恢复`；正常恢复时删掉。
  如果程序在"静音录制"中被强制结束（任务管理器结束、崩溃、断电），下次启动看到残留标记会**自动帮你把声音打开**并写日志。
- 已有的「声音」按钮仍然是同一件事的手动版（点一下静音，录完自动恢复）。

**代价说清楚**：静音期间**整台电脑都没声音**（不只是游戏，音乐/QQ 也听不到）。
"只有游戏没声音、其他程序照常"在当前 Windows 上做不到 —— 除非哪天系统给出每程序输出设备，或者上
[虚拟声卡方案](#如果想让只静音游戏其他声音照常虚拟声卡方案)（但它的关键一步同样需要每程序输出设备，见上面的前提提醒）。

### 10. 「用时」显示成天文数字、开头黑屏、结尾戛然而止（2026-09-27 晚，已修）

你报的三件事，加上修的过程中挖出来的三个更要命的旧 bug。

#### 10.1 队列「用时」列显示 `63926114748s`

那是 `DateTime.Now - DateTime.MinValue` 的秒数（≈2026 年）。原因：**只有单录路径会给任务记开始时间，并行路径从来没记过**，
而列表是按 `Ended - Started` 算的。已修：并行也给每个任务记开始时刻；显示加保护（两个时间都有值才算）；
并且统一改成 `2分09秒` 这种人话（列表、日志、完成弹窗都改了）。

#### 10.2 每段开头 5~8 秒纯黑

用 `blackdetect` 量了你 14:05 那批（**并行**录的）：开头黑屏 **4.9 / 6.9 / 8.1 秒**。
原因：并行是「先开录 → 再带 rep 重启游戏实例」，而游戏启动后要初始化 DirectX / 读 rep，这段时间窗口是纯黑。
**单录没这个问题**（实测旧样本开头只有 0.3 秒黑），因为它开录时游戏画面已经出来了 —— 我一开始误判成单录也黑，
白折腾了一轮（那段"等画面"逻辑已撤掉，注释里留了结论免得以后再踩）。

修法（并行）：录制中每秒截一次每格的采集源，记下「画面真的出现」的时刻，切分时用 `-ss` 精确剪掉。
实测每格剪掉 **12.3~12.4 秒**，成品里 ≥0.15 秒的黑段**一处都没有**。

#### 10.3 结尾拖一段黑、"戛然而止"

实测：单录结尾 **2.38~2.45 秒**纯黑（游戏退出的黑 + "停录前等待 2 秒"，两者都录进去了）；并行 0.78~1.02 秒。

- **单录**：游戏退出时若画面已经黑了，就不再等那 2 秒；录完再让 ffmpeg 把结尾残余黑段**流复制剪掉**
  （`-c copy`，不重编码，几秒完事；任何一步不对就保留原文件，绝不拿成品冒险）。
  实测：结尾黑 **2.4 秒 → 0.35 秒**，开头 0 秒。
- **并行**：每格按「最后一次看到画面」和「游戏退出时刻」里更早的截止；切分时再加 **0.6 秒淡出**（视频+音频）
  —— 并行本来就要重编码，等于免费。实测头尾黑段全为 0，结尾是平滑淡出而不是硬切。

#### 10.4 顺手挖出来的三个旧 bug（都会让整段录像全黑 / 后续全部失败）

修复 10.2/10.3 的过程中，我在验证里踩到了三个**原本就存在**的坑，都已修：

| 现象 | 原因 | 修法 | 实测 |
| --- | --- | --- | --- |
| 单录整段**全黑**（音频正常） | 并行录制会临时隐藏单文件用的画面采集源；如果那次程序被强制结束（任务管理器/崩溃/断电），隐藏状态就留在 OBS 里，而单录前程序从不检查 | 准备 OBS 时强制显示一次 + 每次单录前兜底检查 | 同一段录像 **4.7 MB（34.6 秒全黑）→ 86.8~87.2 MB**（正常画面） |
| 单录整段**全黑**（另一个原因） | 采集源是按**窗口标题**匹配窗口的，而游戏自己的标题在启动约 2 秒后会变（实测：`搶曽旕憐揤…` 日文乱码标题 → `东方非想天则 Giuroll…CN`），标题一变采集源就抓不到窗口 | 跟并行一样：开录前把窗口标题强制改成固定 ASCII 记号再绑定，录制期间看守着改回来 | 绑定日志现在是 `th123 录制中:th123_110a:th123.exe` |
| 崩溃后后续全报 500、OBS 一直录 | OBS 是独立进程，程序被强杀时它不会跟着停，会一直录下去（写满磁盘），且 `SetVideoSettings`/`StartRecord` 之后全失败 | 准备 OBS 时先查 `GetRecordStatus`，发现还在录就停掉并等它收尾 | 日志：`发现 OBS 里还留着一段没停的录像（上次程序被强制结束留下的），已停止它` |

### 11. 一次录 6 个：全都没声音、开头切太多、按钮重复、游戏开两遍、没有保存询问（2026-09-27 深夜，已修）

你报的 6 条，按严重程度排：

#### 11.1 并行成品全都没声音 ← 这是我上一版引入的，最该骂

6 个成品里**一个音频流都没有**（`ffprobe` 只看到 `video`）。原因：我给并行切分加"结尾淡出"时写错了一处 ——
把 `,afade=t=out:st=…:d=0.6` 直接拼在输出参数后面（正确写法是走 `-af afade=…`），ffmpeg 解析失败；
而 `SplitOne` 里有三次尝试，前两次（带指定音轨、带默认音频）都失败之后，**退化成第三次的 `-an`（无声）**，
于是每个成品都没声音，日志里也看不出来。

已修：改成 `-af afade=…`；并且以后万一又退化成无声，日志会明确写一行告警（不再悄悄出无声视频）。
实测（5 格并行，修复后）：5 个成品**全部有 audio 流** ✓。

#### 11.2 每局开头都被切掉几秒 ← 也是我上一版引入的

原因：并行是"开录 → 再启动游戏 → 绑定采集源"，而采集源是按**窗口标题**匹配窗口的；游戏启动约 2 秒后会把
自己的标题从日文原版改成中文版，**标题一变采集源就抓不到窗口**。我当时靠"录制中每秒截图找第一帧真画面"
来算开头的剪裁点，而录制刚开头那十几秒截图一直返回黑帧 → 算出来的"画面出现时刻"其实是**采集恢复的时刻**，
那时对局已经打了十几秒 → 于是每局开头都被剪掉一截。

已修，两处：

1. **流程改成**：带 rep 启动 → 等窗口出现 → 量尺寸定画布 → **先把标题强制成 `th123 #N`** → 开录 → 建源绑定，
   并且录制期间 1 秒一次看守标题（游戏改回去就改回来）。采集源从开播一开始就能抓到。
2. **剪裁点改成录完之后再算**：直接把合并录像里这一格裁出来、以 0.2 秒为间隔逐帧看亮度，找出**真正的**第一帧
   有画面的时刻；**找不到就返回 0（不剪）** —— 宁可多留一点黑，也绝不误删画面。

实测：成品开头现在是「读盘画面 → 第壱戦 ROUND 1」✓（开局每一秒都在），开头残留黑只有 0.2~0.5 秒（游戏自己的）。

#### 11.3 三个按钮功能重复 → 合并成一个「开始录制」

- 列表里**选中了** rep → 只录选中的那些（明确选中 = 一律重录，不管之前录没录过）
- **没选中** → 录队列里最靠前的那些待录 rep
- 要录的数量 ≥2 → 按「同时录制数量」并行，超过就自动分批；只有 1 个 → 走普通单录

「并行录制×N」「录制选中的」两个按钮已删除（逻辑并进「开始录制」）。

#### 11.4 游戏被开了两遍（先开 6 个停在标题画面 → 全杀掉 → 再开 6 个）

那是"先把标题/采集源/音轨摆好再开录"的老做法。现在**只开一次**：带 rep 直接启动 → 等窗口 → 定画布 →
强制标题 → 开录 → 建源绑定。开播前那点黑屏由 11.2 的剪裁处理。
实测日志从「第 1 个实例已启动」到「已开始录像」共 ~8 秒，不再有第二轮启动。

#### 11.5 并行录完没有「视频放哪里」的询问

并行这条路以前压根没接这个逻辑（只有单录会问）。已补上：**一批录完弹一次**询问，选「另存到文件夹」就把这一批
全部搬过去，勾「本队列后面录好的也都这样处理」就记住不再问。

#### 11.6 队列「用时」要显示视频时长

以前显示的是任务耗时（并行还包括开游戏、切分的时间）。现在**优先显示成品视频的真实时长**——
直接解析 mp4 里的 `moov→mvhd`（不依赖 ffprobe），日志里也分开了：`视频时长 3分05秒（任务耗时 5分12秒）`。

```
21:45:43  并行：每格画面 640×480          ← 这时量的是"游戏窗口还没被 WindowResizer 放大"的尺寸
21:45:46  并行：第 1 格源真实尺寸 640×480 → 渲染成 640×480（scale 1）；回读画布内尺寸 0×0   ← 占位值
```

### 14. 成品左右两边那条"亮线/轮廓"：查清了，两处都修（2026-09-27 深夜）

现象：成品视频最外圈（尤其右边缘）有一条 1~3 像素的亮线，看着像"边缘不和谐"。

**查证**（都用整段视频的"列平均亮度"量化，成品 1440 宽）：

| 检查 | 结果 |
| --- | --- |
| 游戏窗口客户区 | 640×480、比例 1.3333（正好 4:3，窗口本身没问题） |
| 成品里 HUD 的位置 vs 游戏窗口 | 血条最左：窗口 83px、成品换算 80px → **取景一致**，不是"多录/裁掉了两侧" |

| 最大逐列跳变 | 并行成品 **15.0**（x=2 / x=1438） |

**根因**：
1. **并行**：每格的采集源是"亚像素"缩放（边界框）摆到 `x=0/640/1280…` 的，格与格之间会漏 1~3 像素的**邻居画面（亮）**或**画布黑边（暗）**，切分时按整格裁就把那条线带进成品 —— 就是"OBS 把窗口贴在一起"的意思，只是只有 1~3 像素。
2. **单录**：WGC 抓 640×480 游戏窗口时，最左/最右 2~3 像素本身就带亮边（整段列平均：最左列 82.6，第 3 列起 45.6）。

**修法**（两处都已实测）：

- **并行切分**：每格往里裁一圈 —— 设置项 `ParallelEdgeInset`（默认 **6**，单位是"成品像素"；换算到 640 宽的格子是 3 像素），裁完再缩放到 1440×1080。实测最大跳变 **15.0 → 4.2**，最外圈 25,25,24.9 均匀。
- **单录**：用 OBS 的**源裁剪**把源最外圈裁掉 —— 设置项 `SingleEdgeInset`（默认 **4**，源像素），等比裁 → 画面不变形、**不用重编码**。实测最大跳变 **20.6 → 4.1**，最外圈 42.5,42.4,42.2 均匀。
- 想完全不动就把这两个数值设成 0；想更保险可以加大（代价是边缘多损失一点点，1 像素 ≈ 0.07%）。

> ⚠ 顺带记一笔：给单录试过"把源放大一点点（overscan）来防黑线"，**反而在最左边引入了一条 1 像素亮线**（最左列 62.9、第 2 列起 43.7），已撤掉并在代码里留了注释，别再试。

验证脚本：`验证-边缘裁切.ps1`（真录并行 3 格 + 单录 1 条，然后跑列平均给出"最大逐列跳变"）。

### 19. 让软件能在别人的电脑上直接用（2026-09-28 深夜）

#### 19.1 并行切分不再写死 NVIDIA 编码器

原来切分固定用 `h264_nvenc` ✗ —— **A 卡 / 核显的电脑会直接失败**（找不到编码器，三次尝试全挂）。
现在改成"编码器梯子"：

| 顺序 | 用的编码器 | 参数 |
| --- | --- | --- |
| 1 | 设置里的（默认 `h264_nvenc`） | `-preset p5 -tune hq -rc vbr -cq N -b:v 0` |
| 2 | `libx264`（软件编码，任何机器都有） | `-preset medium -crf N`（nvenc 的 `-rc/-cq` libx264 不认，所以每档带自己的参数） |

### 20. 清晰度、切分提速、录像音量、OBS 空录保护（2026-09-29）

#### 20.1 画面对比"变糊了" → 放大全部改成点采样（neighbor）

用户拿自己录的成品和软件录的成品对比：软件录的明显更糊。两条原因：

1. **单录**：OBS 的画布是 1440×1080，而游戏窗口只有 640×480 → OBS 用**双线性**把它拉大 ✗ 整体发软；
2. **并行切分**：`-vf scale=...,flags=lanczos` ✗ 像素画用 lanczos 放大本来就偏软。

修法：

- **单录**：开录前把 OBS 画布/输出设成**游戏窗口的原生尺寸**（一般 640×480，OBS 完全不缩放），
  录完再用 ffmpeg `scale=1440:1080:flags=neighbor`（点采样）放大 → 保留硬像素；
- **并行切分**：放大同样改成 `flags=neighbor`。

> 参考：用户自己那条"清晰"的录像，其实就是 16:9 拉伸的**点采样**（块状硬边），所以看起来更锐。

#### 20.2 切分提速：并发切分（默认同时 3 个 ffmpeg）

并行录完只有**一张**合并视频，要按格裁成 N 个文件，这一步是重编码、最花时间。原来是**一格一格串行**切 ✗。
现在同一时间跑 `SplitParallel`（默认 3，可改 1~6）个 ffmpeg，总时间大约除以这个数。
（N 卡同时编码路数有限，设太大反而会回退到很慢的软件编码，所以默认 3。）

#### 20.3 新设置：录像音量（增益）

用户问"录制时调电脑音量会不会影响录像音量"。答案是**不会**：

- OBS 抓的是**进程音频流**（`wasapi_process_output_capture`），任务栏那个音量调的是**输出设备** ——
  端点静音都掐不断它（README 第十一节实测：设备静音后录像里声音照旧）；
- 真正会影响录像的只有 Windows「音量合成器」里 **th123 那一条**（实测：那条静音后录像电平从 -23.7 dB 掉到 -41.1 dB）。

想"提前把录像音量定好"，用新设置 `RecordVolume`（默认 1.0 = 原样；2.0 = 两倍/+6dB；上限 20）——
程序用 `SetInputVolume` 直接设 OBS 音频源的音量倍数，**不重编码**。

#### 20.4 日志轮转（这次排查的教训）

以前只写同一个 `RepRecorder.log`，下次运行就把上次的记录盖掉了 —— 出过错却查不到。
现在每次启动先把上一次的日志挪成 **`RepRecorder-上次.log`**。

#### 20.5 修复"录完一批什么都没拿到、直接报错"（用户 #5）

**实测证据**（程序日志 + OBS 日志一起看）：

```
10:47:34  并行：停止录像失败 OBS 请求 StopRecord 失败：501
10:47:34  并行录制结束，合并文件：（空）
10:47:34  并行录制：没有拿到合并视频文件，无法切分
```

而 OBS 那边的日志里，**连一行"录制开始"都没有** ✗ —— 也就是说 `StartRecord` 返回了成功，但 OBS 根本没开始录；
程序却照着"正在录"等满了整局（3 分钟），最后 `StopRecord` 报 501、拿不到文件。用户那次轮录（10 个 rep，6+4）
就是这样：第一批 6 个白录，第二批 4 个才成功。

修法四处：

1. 并行**开录前**先 `StopObsRecordingIfAny()`（清掉 OBS 里可能卡住的录像状态）—— 以前并行这条路完全不做这步；
2. `StartRecord` 之后 1.5 秒查 `GetRecordStatus.outputActive`：不在就重试一次，
   还不在就**立刻中止这一批并明确报错**（"OBS 没有真正开始录像（已中止，避免白等）"），不再白等 3 分钟；
3. `StopRecord` 失败时，**自己去录像目录里找刚录出来的那个文件**当合并文件（按时间/大小筛），
   以前这里直接放弃 → 就是"什么都没拿到"；
4. 日志轮转（20.4），保证下次能查。
