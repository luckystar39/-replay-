## 执行前的裁定（Ruling）

- **R1 不开工作树**：执行流程默认在 git worktree 里隔离，但本项目 git 归用户自己管
  （记忆 `user-manages-git`），而且一直是在原地 `main` 上开发的。用户 2026-10-12 明确说「动手」，
  即在此工作副本上直接改。*代价*：没有 git 隔离；退路是 `RepRecorder-旧版WinForms\`（完整旧版快照）
  与 `/tmp` 里的临时副本。
- **R2 不提交**：流程默认每个任务结束提交一次，用户规矩是 git 归他自己管。**每个任务以
  「验证脚本通过 + 本台账一行」作为完成标志**，不产生提交。*代价*：没有逐任务的 git 回滚点；
  由用户自己的提交节奏兜底。
- **R3 台账放本项目 `文档\`**，不用 `.superpowers/sdd/`（用户看不见它，而且会往仓库根加东西；
  同一裁定在 `_移植进度.md` 的 R2 里已经立过）。*代价*：流程自带的 `task-start` / `task-done`
  脚本用不了（它们依赖 git），手动维护。
- **R4 「测试」= PowerShell 验证脚本**：本工程项目没有单元测试框架，它的测试就是
  `测试\验证WPF-*.ps1`（同一裁定见 `_移植进度.md` 的 R3）。因此每个任务里的 RED 步骤是
  「跑那条脚本／那条命令，看它现在确实是坏的结果」，GREEN 是「改完再跑，看它变好」。
- **R5 需要眼睛和耳朵的验收**：计划里有若干步是人工验收（打开 mp4 听声音、拖边框感受卡顿、
  点对话框选文件夹）。我是 agent，**看不到屏幕也听不到声音**。处理办法：能自动化的照做
  （调试接口 + UIA + 截图，截图我能读）；**真正只能靠人的，在对应任务的台账行里标
  `待用户人工确认` 并写清要看什么**，最后汇总给用户。*代价*：这些点在我这一侧的完成度
  只能到「脚本绿 + 代码路径对」，不能声称已经人眼验过。

### Task B10：截图采样间隔（B18）— **按裁定不实施**，改为删掉同区域的死变量

- **Ruling（Task B10）：不做"1 秒 → 2 秒"。** 理由：
  1. **spec 给的理由不成立。** 它写的是"2 秒的精度照样够（裁剪边界本来还有
     `SingleEdgeInset`/`ParallelEdgeInset` 的余量兜着）" —— 但那两个 inset 是**空间**上的
     （每格往里裁几个像素），跟**时间**轴上的采样精度没有关系，兜不住。
  2. **代价是用户看得见的**：`cellLastSeen`（并行）与 `lastVisibleSec`（单录）驱动的都是
     **结尾裁黑**（`seen = cellLastSeen[i] + 0.25` / `keep = lastVisibleSec + 0.25`）。
     采样放宽到 2 秒，这两个值最坏早 1 秒多，成片结尾就多留 1 秒多的黑。
  3. **收益很小**：这里是每格每秒一次 `GetSourceScreenshot`，参数是 **320×240 jpg q60**，
     6 格满格也只有 6 次/秒 —— 对 OBS 是毫秒级负载。用"每支视频结尾多一截黑"换它不划算。
  4. 这条的取舍只有用户能拍板（他一直在意成片画质）。改回去是**一处改动**：
     并行那处没有计数器（靠循环节拍）、单录那处是 `ticks % 2 == 0`。
     我在这两处都留了注释说明"别放宽到 2 秒，以及为什么"，免得后人又照着当初那条 spec 改一遍。
- **顺手查出来的真东西**：`cellHead` 是**只写不读的死变量** —— 它只在录制循环里被赋值
  （`if (cellHead[i] <= 0) cellHead[i] = sec;`），从来没有任何地方读它做裁剪：
  开头的黑是切分前 `AnalyzeCellHead(gridFile, …)` **逐帧**（5 帧/秒）算出来的，精度比这些采样高得多。
  所以那次采样实际上只服务 `cellLastSeen`。**删掉** `cellHead`（声明、分配、写入那三处），
  并把采样块的注释改成"这里只管结尾，开头的黑靠 AnalyzeCellHead"，免得以后再有人以为它管两头。

psnr:  PSNR y:inf u:inf v:inf average:inf min:inf max:inf
ssim:  SSIM Y:1.000000 (inf) U:1.000000 (inf) V:1.000000 (inf) All:1.000000 (inf)

## 追加二：DPI 换算方向修对了（画质差的第一层原因，2026-10-13）

用户的抱怨是"后面三个的画质太烂"。查下来第一层原因是**程序自己丢像素**：

程序量到游戏窗口的客户区之后，又拿 `dx/96`（本机 1.5）去**除**，于是把 640×480 的窗口
按 **427×320** 交给 OBS 采。三个进程的 DPI 感知实测：

| 进程 | `GetProcessDpiAwareness` |
|---|---|
| **th123.exe（游戏）** | **PER_MONITOR_AWARE (2)** ← 整合包的 mod 加载器设的 |
| RepRecorderWPF.exe（本程序） | SYSTEM_AWARE (1) |
| 我的探针（PowerShell） | UNAWARE (0) |

窗口实际尺寸（同一个窗口，两种视角）：

| 视角 | 客户区 |
|---|---|
| DPI 不感知（Windows 虚拟化过的） | 426×320 |
| **DPI 感知（真实物理像素）** | **640×480** |

- 游戏是 DPI 感知的 ⇒ **Windows 没有对它做位图拉伸**，640×480 就是真像素；
- 程序也是 DPI 感知的 ⇒ 它量到的 640 本来就是物理像素（和 OBS 画布同一个单位）——
  **再除 1.5 就是多除了**。而 427 恰好等于"不感知进程看到的虚拟尺寸"，所以一直没人看出来。
- 代码里那段注释（"非想天则是 DPI 不感知的老程序，Windows 会把它位图拉伸"）来自 2026-10-05
  一个"**假装是游戏**的探针窗口"——那个探针确实不感知，拿它推断真游戏推错了。
- 顺手把 `> 1920 || > 1440 就重置成 640×480` 那道闸门放宽到 4096：老门槛是按"除以 1.5 之后"
  的数值定的，改成物理像素之后**全屏 2560×1600 是正常值**，用老门槛会把它误判成异常。
  真的偏大不用怕，下面"压到输出尺寸"和 `GridScaleToFit` 两道闸门会等比缩好。

**改法**：`WindowDpiScale` → `WindowPixelScale`，感知时系数 1.0，只有真不感知才 `* dx/96`；
调用处由除改成乘。

## 追加三：游戏窗口本身的大小（用户要求"变大一点，记住一个大一些的"）

游戏窗口尺寸由 **WindowResizer** 模块的 `modules\WindowResizer\WindowResizer.ini` 决定

**先查清了三件事（都实测）**：

| 问题 | 实测结论 |
|---|---|
| 按 Alt+大键盘1/2 会写回 ini 吗？ | **不会**（按完 ini 的字节数、修改时间都不变） |
| 那 ini 什么时候会被写？ | **游戏【正常退出】时**（`WM_CLOSE` 关掉游戏之后，ini 从 1280×960 变成 640×480） |
| 录制流程里让用户按 Alt+2 管用吗？ | **不管用** —— 本程序结束一批时是**强杀**游戏（`g.Kill()`），强杀不触发写回 |

**外部 `SetWindowPos` 撑大之后，游戏会不会按新尺寸重新渲染？**（这是方案能不能做的前提）
抓同一局的画面比过：外部撑到 1280×960 之后，底部六角形/HUD 的**硬边像素块和 640×480 时同一风格**，
不是"把 640×480 拉大"的糊图 → **会重新渲染，方案可行**。
⚠ 诚实说明：这是**看图判断**（我试过的几个数值指标都因为两次抓的是不同时刻的画面而没法干净地比），
而且抓对照图时还失败过一次（`gdigrab` 抓到别的程序去了）。

**做法**：开录前（量尺寸之前）对每个游戏窗口 `SetWindowPos`：

- **只放大、不缩小**（用户自己设了 3x/全屏一律不动）；
- 1x/2x 里挑能用的最大那个（都是 640×480 的整数倍 —— 模块自己的说明：非整数倍会让字发糊）；
- 同时受"切分输出尺寸"和"屏幕工作区（含程序摆放窗口用的 +320/+60 偏移）"约束 → 小屏自动退回 1x；
- 撑完等 1.5 秒复核，被改回去就再撑一次（模块启动时也会按 ini 设一次，谁先谁后不一定）。

**端到端验证**（把 ini 设回 **1x**，模拟没改过设置的普通用户，跑真实 6 格）：

```
并行：已把 6 个游戏窗口撑到 1280×960（每格按真实像素采；窗口越大成品越接近原生，代价是中间文件更大）
并行：每格画面 1280×960，3 列 × 2 行，中继画布 3840×1920
```

成品参数与"模块自己撑的"那版**等价**：1440×1080/60fps、19.4~23.5 Mbps、170~204 MB
（模块撑的：19.5~23.1 Mbps、173~201 MB）；6 条音轨指纹各不相同。

**顺带的好消息**：整合包那份 ini **可以保持默认的 1x**（小屏用户手动玩也舒服），录制照样按 2x 采。

## 追加五：切分时的 CPU 占用（用户报"跑满"，2026-10-13 晚）

**用户报告**：录完 rep、刚开始切分那一刻 CPU 跑满，任务管理器里那个进程**是 ffmpeg**。

**第一次量，假设被推翻。** 我拿 6 个真实成品拼了份"同规格"素材（3840×1920@60 + 6 条音轨），量出来
抽帧分析只占 **2.0 个核**、切分 **3.2 个核**（24 核的 8% / 13%）—— 根本够不到"跑满"。
**原因：那份合成素材是我用 NVENC 重编的，比 OBS 录出来的好解得多**（用户真实文件切分要 114 秒，
同样的活我的合成素材只要 60 秒）。**教训：这种"解码开销"类的问题，必须拿真实中间文件量。**

**改用真实文件（留了一份真实中间文件，见下）后的对照：**

| 环节 | 软件解码（改之前） | 显卡解码（现在） |
|---|---|---|
| 抽帧分析 | 11.2 秒 / **4.29 个核** | 10.7 秒 / **0.38 个核** |
| 切分（两组并发） | 71.2 秒 / **6.57 个核** | 74.2 秒 / **1.82 个核** |

**改法**：`HwaccelPrefix()` —— 在 ffmpeg 命令行最前面加 `-hwaccel cuda`（解码走显卡的 NVDEC），
抽帧分析和切分两处都加，且**只在"本来就在用 NVENC"时才加**（没 N 卡的电脑本来走 libx264，不碰 cuda）；
两处都有兜底：加了它那次失败会自动退回不带它的写法（切分那边多一档重试，不影响成品）。

**必须说清楚的两点**：
- **时间基本没变**（71.2 → 74.2 秒、11.2 → 10.7 秒，都在噪声里）。这次修的是 **CPU / 响应性**，不是速度。
  ⚠ 我中途一度说"快了 1.6 倍"是**错的** —— 那是拿用户较长的 rep 和我较短的对比较出来的，苹果比橘子。
- **我量到的峰值只有 6.57/24 = 27%，够不到用户说的"跑满"** ✗。可能是 ffmpeg 起解码器那一两秒的瞬时爆发
  （hwaccel 也不再开十几个线程，这种爆发也没了），也可能当时还有别的进程参与。
  **下次用户录的时候要再看一眼**；如果还满，接着查。

**留下了一份真实中间文件**：`%TEMP%\rr6\grid-real.mp4`（1.19 GB，真机 6 格 3840×1920 的原版）。
以后要验"命令级"的改动（切分/抽帧/滤镜），用它就行，**不用再录一批**。

## 追加七：切分编码器加上「AMD 显卡」一档（AMF，2026-10-14）

**起因**：用户问"要是用户用的是 AMD 显卡呢"。查下来结论是 —— 我们只认 NVENC：
编码器梯子里只有 `*_nvenc` 和 `libx264`，解码前缀写死 `-hwaccel cuda`，设置里也只有两档。
**A 卡用户等于"无显卡用户"**：全程 CPU 软解 + x264 软编。
（录制那一步不吃亏：中间文件是 OBS 录的，A 卡用户在 OBS 里选 AMF 就行，与我们的 ffmpeg 无关。）
用户拍板：**加第三档「AMD 显卡」，核显不管**（用核显的人自己有办法）。

**改了什么**（`src/Recorder.cs` / `Core.cs` / `UiDialogs.cs`）

- 抽出 `EncArgsFor(enc, cq)`：三家参数各写一处，**除 libx264 外最后都跟一发 libx264 兜底**。
  ⚠ 以前 `SplitOne` / `SplitGroup` 各写死一份，加一档得改两处、漏一处就是"某条路径静默少试一发"。
- `HwaccelPrefix(enc)` 改成按卡选：N 卡 `-hwaccel cuda`、A 卡 `-hwaccel d3d11va`（Windows 通用硬解）、软编给空串。
  抽帧分析共用这一个函数 → A 卡机器上抽帧分析顺带也吃上硬解了（那条路本来就有"失败退回软解"的兜底 ✓）。
- 界面第三档「AMD 显卡（快）」→ `h264_amf`；说明**另起一行**（就是追加六那个"第三列挤掉下拉框"的坑）。
- 日志措辞：原来无论什么原因都写「多半没 NVIDIA 显卡，已换 libx264 软编」—— A 卡用户看了会以为
  程序认为他没显卡。现在按**实际成功的那一发**说（`退到第 3/4 种参数才成功（CPU 软编）`），
  并且用设置里那个选项名（NVIDIA 显卡 / AMD 显卡 / CPU 软编）。
- 文案同步：两份 `说明-给使用者`、`Core.cs` 里那条 Description。

**AMF 的参数是查出来的，不是猜的**（对包里那个 ffmpeg 跑 `-h encoder=h264_amf`，2026-10-14）：
`-usage transcoding -quality quality -rc cqp -qp_i <CQ> -qp_p <CQ+2> [-qp_b <CQ+4>] -pix_fmt yuv420p`；
h264_amf / hevc_amf / av1_amf 三个都逐个查过。

**实测（本机是 N 卡，只能验"参数认不认"和"没有这张卡时会怎样"）**

| 试的东西 | 结果 |
|---|---|
| 程序会拼的那条 `h264_amf` 命令（带 / 不带 `-hwaccel d3d11va`） | rc=171，报 **`DLL amfrt64.dll failed to open`** / `Failed to create hardware device context (AMF)` —— 是"没有 A 卡/驱动"这种**环境失败**，不是参数错 ✓ |
| 对照：编一个真不存在的选项 `-qp_zzz` | `Unrecognized option 'qp_zzz'` → 参数错长这样 ✓（两种失败能分开） |
| `-qp_b` 给 `hevc_amf` | **不报错**，只打一句 `Codec AVOption qp_b ... has not been used`（当没给）→ 那档干脆不给它 ✓ |
| `-qp_b` 给 `h264_amf` / `av1_amf` | 没有 warning → 是真吃这个参数的 ✓ |
| 把 nvenc 那套（`-tune hq` / `-cq 23`）丢给 `h264_amf` | **也不报错**，同样"has not been used"、静默当没给 → 画质档位悄悄变成 AMF 的默认值。**比报错更阴**，这条值得记住 |

**兜底链（用户选了 A 卡但机器上没 A 卡）**：第 1 发 `d3d11va+h264_amf` 失败 → 第 2 发 `h264_amf` 失败 →
**第 3 发 libx264 软编顶上、成品照样出** ✓ 这就是界面上那句"选错了也不会失败"的依据。

**端到端实测（2026-10-14 12:16，2 格真录，N 卡机器上把设置选成「AMD 显卡」）** —— 日志原文：

```
12:18:03  并行切分：一组 2 格（第 1~2 格，配第 1~2 条音轨），用 AMD 显卡（h264_amf）
12:18:04  并行切分：AMD 显卡（h264_amf）用不了，正在试后面的参数…
12:19:31  并行切分：一组 2 格，退到第 3/4 种参数才成功（CPU 软编）
12:19:31  并行切分完成（第 1 格）：r1.mp4  100.5 MB  视频时长 1分08秒
12:19:31  并行切分完成（第 2 格）：r2.mp4  147.6 MB  视频时长 1分12秒
```

成品正常（1440×1080@60、H.264 + AAC 音轨都在）✓。"第 3/4 种"就是梯子的第 3 发 = libx264，和设计对得上
（4 发 = d3d11va+amf / amf / libx264 / 无声兜底）✓

**额外收获**：这一趟**抽帧分析没有退到软解**（日志里没有"显卡解码抽帧没成"）—— 因为 `-hwaccel d3d11va`
在 N 卡机器上照样能用（D3D11 是厂商无关的）。也就是说选了 A 卡那档时，N 卡机器上的抽帧分析反而也吃上了硬解 ✓

**没验到的（诚实记一笔）**：A 卡真机的**速度和画质**验不了 —— `qp 23` 和 `cq 23` 本来就不等价，
只能等真 A 卡用户反馈；"每组先白失败两次大约 1 秒"也只是估算，没量过。

**以后要加第三家（例如 Intel 核显 QSV）**：同一套路子 —— `EncArgsFor` 加一族、
`HwaccelPrefix` 给它 `d3d11va`、设置里再加一档。
⛔ 但**别再往梯子里堆"自动探测"**：现在是"用户选哪档就用哪档 + 逐级降级"，四发已经够长，
再堆就得在启动时先跑一遍小样本，多一层要维护的状态，不划算。
