# 启动时检查更新 —— 设计（2026-10-10）

做法照抄整合包里 SokuLauncher 那套：**仓库里放一份 `version.json`，安装包作为 Release 附件**。
启动时拉一次清单、比版本号，有新版本就提示。它那份清单长这样（实测拉下来看的）：

```json
[ { "Name": "SokuLauncher", "Version": "2.4.2.0", "FileName": "SokuLauncher.exe",
    "Notes": "### 启动器本体更新 2.4.2.0\n\n- 修复…", "Compressed": true,
    "DownloadLinks": [ { "Type": "Gitee", "Url": "https://gitee.com/…/releases/download/2.4.2.0/SokuLauncher.zip" } ] } ]
```

它是**数组**，因为要更新启动器本体 + 一堆 mod。我们只有一样东西，所以用单个对象。

## 目标 / 不做的事

- **要**：用的人打开软件就知道有新版本，点一次就换好；你发版从十几步缩到"传一个 450KB 的包 + 粘一段 json"。
- **不做**：不静默更新（一定问）；不管 ffmpeg（它不会变，更新包里不含它）；不做多组件清单。

## 一、清单 `version.json`

```json
{
  "Version": "1.1",
  "Notes": "### v1.1\n\n- 修了并行录制……",
  "Sha256": "9f2c…（更新包的 sha256，小写十六进制）",
  "DownloadLinks": [
    { "Type": "Gitee",  "Url": "https://gitee.com/<你>/<仓库>/releases/download/v1.1/RepRecorder-1.1-更新包.zip" },
    { "Type": "GitHub", "Url": "https://github.com/luckystar39/------------2026-06-15/releases/download/v1.1/RepRecorder-1.1-更新包.zip" }
  ],
  "FullPackage": "https://github.com/luckystar39/------------2026-06-15/releases/download/v1.1/RepRecorder-发给别人.zip"
}
```

- 字段名沿用 SokuLauncher 的（`Version` / `Notes` / `DownloadLinks` / `Type`），读起来眼熟。
- ⚠ **必须是合法 JSON**：实测 `JavaScriptSerializer` **不接受尾随逗号**（`{...,}` 直接判为无效）。
  发版脚本生成的一定合法；只有你手改时要注意。写错了的表现是"更新永远查不到"，
  日志里会有一行 `检查更新：invalid（…）`。
- `DownloadLinks` 是数组：**先 Gitee 后 GitHub**，Gitee 拿不到就换一个。
- `Sha256` **必填** —— 没有它程序拒绝自动替换（只给下载页）。发版脚本会自动算，所以不会漏。
- `FullPackage` 给"我 ffmpeg 也丢了"的人，指 GitHub（Gitee 每仓库附件总共只有 1GB，完整包 84.8MB 传几次就满）。

## 二、版本比较

**按数字分段比，不能用字符串比**（`"1.10" < "1.9"`，经典的坑）：

- 按 `.` 切开，每段取前导数字；任一段取不出数字 → 整份清单判为无效（记日志、不提示）
- 短的补 0：`1.1` ≡ `1.1.0.0`，和 exe 里的四段 `1.1.0.0` 能对上
- 只有 `远端 > 本地` 才提示；相等或更低什么都不做（**不做降级**）

## 三、检查流程

- **时机**：WPF 启动、窗口起来之后，起一个后台线程去拉
- **节流**：6 小时内查过就不再查（设置里存时间戳）。免得一晚上开五次、gitee 被敲五次
- **超时 8 秒**；必须带 `User-Agent`（Gitee / GitHub 对空 UA 会 403，这条踩过就知道疼）
- **必须显式开 TLS 1.2**：`ServicePointManager.SecurityProtocol |= SecurityProtocolType.Tls12`。
  别指望运行时默认值 —— 老机器上默认可能是 TLS 1.0，gitee 直接拒
- **一切失败都静默**：没网、超时、json 坏、地址没配 → 只写一行日志，**不弹任何东西**
- **回填给界面走那 2 秒的定时器**（和自动找游戏 / 找 ffmpeg 同一条路子）。
  ⚠ 不用 `Ui.OnUi` 直接回调：它在 `Application` 还没建好时会在调用线程上直接跑（Ui.cs 里那句），
  后台线程撞上就是从非 UI 线程碰控件
- 查到新版 → 弹一个小窗：`发现新版本 v1.1（你现在是 1.0）` + 更新说明 + 三个出口：
  **「下载并更新」** / **「以后再说」**（把这个版本号记进 `SkippedUpdateVersion`，**不再为它弹**） / **「打开下载页」**

## 四、下载与替换

更新包是 **~450KB 的小 zip**（只含 exe + 两份说明，不含 ffmpeg）。

📌 **硬上限 20MB**（`验证WPF-18` 有一条断言钉着它）。本意是挡住"顺手把 ffmpeg 也塞进来"
（那是 217MB，一键更新会变成下 85MB）；取 20MB 而不是贴着当前的 450KB，是因为用户
2026-10-10 说"软件以后可能做大"——留十倍余量，同时和 ffmpeg 仍差一个数量级。

```
1. 下到 %TEMP%\repupdate-<ver>.zip
2. 比 Sha256 —— 不对就删掉、报错、一个字节都不动
3. 解压到临时目录，确认里面的 exe 存在且非空
4. 把【当前正在运行的那个 exe】改名为 <原名>.old      ← 实测：正在运行也允许改名
5. 把解出来的 exe 改名成正式名字                      ← 失败就把 .old 改回来（回滚）
6. 覆盖两份说明 md（zip 里有才覆盖）
7. 下次启动时顺手删掉 .old
```

两个关键细节：

- **目的地是"运行进程自己的路径"**（`Process.GetCurrentProcess().MainModule.FileName`），
  **不是 zip 里那个文件名**。所以开发目录的 `RepRecorderWPF.exe` 和分发出去的
  `RepRecorder.exe` 都能正确替换。
- **第 5 步失败必须回滚**。最坏情况是"软件没了"，所以顺序刻意做成：先把新的准备好（第 3 步）、
  再动旧的（第 4 步）、最后一步只是改名（几乎不会失败）。

替换完提示"已更新到 v1.1，下次打开就是新版"，并给一个**「马上重启」**。
（启动时才提示，所以这时不可能正在录制，重启是安全的。）

**下载/替换失败时**（没网、超时、sha 不对、目录没写权限）：不关窗，把失败原因写在小窗里
（sha 不对要写明"文件可能没下全"），并留一个**「打开下载页」**的出口让人手动下。
**任何情况下都不留下一个坏 exe**：要么成功、要么一个字节都没动。

## 五、托管分工

| 放什么 | 放哪 | 为什么 |
| --- | --- | --- |
| `version.json` | Gitee 仓库（一个**新仓库，只放这一个文件**） | 国内直连快（实测 0.34 秒） |
| 更新包 450KB | Gitee **和** GitHub 都传 | Gitee 是国内一键更新的主路；GitHub 那份是备用 |
| 完整包 84.8MB | GitHub Release | Gitee 单文件上限 100MB、每仓库附件总共 1GB，传几次就满 |

⚠ **Gitee 那个仓库不需要放你的源码**，它就是"放一个清单文件的网盘"。清单用网页编辑器改，
**不用会 git**（和你 VSCode 里那套是两条互不相干的线；你本地 git 只是多了个版本号改动）。

## 六、发版流程

双击 **`发版.bat`**，输入新版本号（例如 `1.1`）→ 它自动：

1. 改**两处**版本号：`Core.cs` 的 `AppInfo.Version` + `AssemblyInfo.cs` 的两条
2. 调 `编译.bat`
3. 跑 `验证WPF-00`（它会核对版本号在源码、exe 元数据、日志里三处一致，漏改就红）
4. 调 `同步到所有文件夹.bat`（更新分发目录 + 完整包）
5. 生成 `_发版\RepRecorder-1.1-更新包.zip`（只含 exe + 两份说明）
6. 算它的 sha256，写出 `_发版\version.json`（网址按配置拼好，直接可用）
7. 写出 `_发版\照着做-发版.txt`（手把手三步 + 要粘贴的内容）
8. 打开 `_发版\` 文件夹

然后你手动：**传更新包到 Gitee 和 GitHub 各自的 Release `v1.1`** → **把 version.json 内容粘到 Gitee 仓库** → 完整包传 GitHub。

脚本开头有一行配置（只填一次）：

```
set GITEE=<你的用户名>/<仓库名>          ← 还没定，先留空
set GITHUB=luckystar39/------------2026-06-15
```

⚠ `.bat` 按仓库既有规矩写成 **GBK、不写 chcp**（`chcp 65001` + UTF-8 会让 cmd 按字节错位解析整个文件）。
`.txt` 清单写成 **UTF-8 带 BOM**，免得记事本显示成乱码。

## 七、清单地址写哪

写死在 `Core.cs` 的一个常量里（不给用户改，免得被随意指走）：

```csharp
// 更新清单地址。留空 = 不检查更新（仓库还没建好时就是这个状态）。
// 建好 Gitee 仓库之后填 https://gitee.com/<你>/<仓库>/raw/main/version.json
public const string UpdateManifestUrl = "";
```

留空时：启动检查直接跳过、日志写一句"未配置更新地址"。**填一处、重新编译就生效**，功能本身不用改。

## 八、测试（`验证WPF-18`）

不依赖网络 —— 清单用本地 `file://` 喂，替换用临时目录当靶子（**绝不能拿正在运行的程序当靶子**）：

| 断言 | 手段 |
| --- | --- |
| 版本比较：`1.10 > 1.9`、`1.1 == 1.1.0.0`、`2.0 > 1.9.9.9` | 调试命令 `cmpver:<a>|<b>` |
| 有新版本 / 已是最新 / 远端更低不提示 | `updatecheck:<file://清单路径>` |
| 坏 json、缺 `Version`、地址不存在 → 不崩、返回 error、**不弹窗** | 同上，喂各种坏清单 |
| **Sha256 不对 → 一个字节都不动** | `updateapply:<zip>|<临时目录>` |
| 正常替换 → 目标变成新内容、旧的成为 `.old` | 同上 |
| 目标目录只读 → 报错且**回滚**（原文件还在） | 同上 |
| 「以后再说」记住版本 → 同一个版本不再提示 | 设置文件 + 重开 |

## 九、我要坦白的风险

1. **这个功能让程序开始"从网上拿可执行文件并运行"**，之前它只读你指定的本地文件。
   防线：HTTPS + 你仓库账号的安全 + `Sha256`（**只防传输损坏，不防你仓库被别人改了** ——
   清单和包在同一处，能改仓库就能改清单）+ **不是静默的**（一定弹窗）。
   哪天 Gitee 或 GitHub 账号被盗，这条链路就是攻击面。
2. **SmartScreen**：换 exe 必然再弹一次「无法验证发布者」。功能没问题，但别指望用户完全无感。
3. **`发版.bat` 会改源码文件**（版本号那两处）。它按正则在特定行上改，改了会打印 diff 供你核对；
   但它毕竟是自动改源码，第一次用请先看一眼改了什么。
